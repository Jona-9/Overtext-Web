## 1. Propósito de las Capas Service y Controller

La arquitectura multicapas de Spring Boot en OverText divide estrictamente la lógica de la aplicación en capas desacopladas:
- **Capa Service:** Orquesta las reglas del negocio, administra la transaccionalidad declarativa (`@Transactional`), gestiona la conversión bidireccional entre entidades de persistencia (`Entity`) y objetos de transferencia (`DTO`), y realiza validaciones de unicidad o existencia de relaciones (como la pertenencia de categorías o duplicidad de emails).
- **Capa Controller (REST):** Publica la frontera HTTP de la aplicación mediante `@RestController`, asigna los verbos canónicos (`GET`, `POST`, `PUT`, `DELETE`), activa la validación declarativa de parámetros y cuerpos (`@Validated`, `@Valid`), y retorna exclusivamente objetos serializados en formato JSON con códigos de respuesta HTTP semánticos (`200 OK`, `201 Created`, `204 No Content`, `400 Bad Request`, `404 Not Found`).

### Gestión de Transaccionalidad (`@Transactional`)
En cumplimiento de las buenas prácticas de Spring Framework:
- Cada clase de servicio está decorada a nivel de tipo con `@Transactional(readOnly = true)`, optimizando las operaciones de lectura contra el pool de conexiones HikariCP y la base de datos Supabase PostgreSQL.
- Los métodos que efectúan modificaciones en el estado persistente (`crear`, `actualizar`, `eliminar`, `registrar`, `darDeBaja`) están anotados con `@Transactional` explícito, garantizando aislamiento ACID y reversión automática (`rollback`) ante cualquier excepción en tiempo de ejecución.

## 4. Implementación de Validaciones en Controladores (Requisito Rúbrica P3)

La rúbrica de la P3 exige demostrar la intercepción y validación de datos tanto en peticiones de lectura (`GET`) como de escritura (`POST`):

### 1. Validación en Método `GET` (`@Positive`)
Se implementa a nivel de parámetro mediante `@PathVariable @Positive(message = "El ID debe ser positivo") Long id` y la anotación `@Validated` en la cabecera del controlador.
- Si el cliente envía un identificador negativo (por ejemplo `/api/productos/-5`), Spring Framework rechaza la petición a nivel de controlador mediante Bean Validation antes de consultar la base de datos.

### 2. Validación en Método `POST` (`@Valid`)
Se implementa anteponiendo `@Valid` al cuerpo `@RequestBody ProductoRequestDTO dto`.
- Si el cliente omite campos obligatorios o envía valores que violan las 5 reglas Bean Validation (`@NotBlank`, `@Size`, `@NotNull`, `@Positive`, `@Email`), Spring Framework interrumpe el despacho y responde automáticamente con **HTTP 400 Bad Request**.

## 5. Códigos de Respuesta HTTP Semánticos

Los controladores implementan las respuestas REST estándar mediante `ResponseEntity`:
- **HTTP 200 OK:** Respuestas exitosas de consulta (`GET`) y actualización (`PUT`).
- **HTTP 201 Created:** Creación y persistencia exitosa de un nuevo recurso (`POST`).
- **HTTP 204 No Content:** Eliminación exitosa (`DELETE`).
- **HTTP 400 Bad Request:** Peticiones que no superan las validaciones de entrada (`@Valid` o `@Positive`).
- **HTTP 404 Not Found:** Identificadores inexistentes en la base de datos retornando `ResponseEntity.notFound().build()`.
