## 1. Introducción y Justificación de la Infraestructura en la Nube

En el marco del desarrollo de la **Práctica Calificada 3 (PC3)** para la plataforma de comercio electrónico OverText, se ejecutó la transición desde una arquitectura web acoplada con renderizado del lado del servidor (SSR con Thymeleaf en P2) hacia un **Backend RESTful puro desacoplado**. Este cambio estructural exige una base de datos centralizada, escalable y accesible de forma concurrente por los diversos integrantes del equipo y los clientes consumidores de la API (Postman, scripts cURL y futuros frontends móviles o web).

Para cumplir con el criterio de conexión a base de datos relacional exigido en la rúbrica oficial (PostgreSQL / MySQL), se seleccionó **Supabase**, una plataforma *Backend-as-a-Service* (BaaS) sustentada íntegramente sobre un motor **PostgreSQL 17.11** administrado en la infraestructura cloud de **Amazon Web Services (AWS)** en la región `us-west-2` (Oregon).

### Ventajas Técnicas de Supabase PostgreSQL frente a una BD Local:
1. **Disponibilidad y Concurrencia Centralizada:** Elimina los desfases de esquemas entre miembros del equipo al no depender de instancias locales de MySQL/Postgres en Docker o XAMPP.
2. **Pooler Nativo de Conexiones:** Integra soporte de pooling transaccional (PgBouncer/Supabase Pooler) que gestiona eficientemente las conexiones entrantes bajo entornos de red restringidos mediante IPv4 y autenticación SSL obligatoria (`sslmode=require`).
3. **Observabilidad y Monitoreo en Tiempo Real:** Interfaz web visual con Table Editor, SQL Editor y métricas de consumo de cómputo (CPU, RAM, cuotas de I/O) en tiempo de ejecución.
4. **Cumplimiento Estricto de Estándares ANSI/ISO SQL:** Soporte nativo para tipos avanzados (`BIGSERIAL`, `JSONB`, `BOOLEAN`, llaves foráneas con eliminación restringida y verificación con cláusulas `CHECK`).

## 2. Definición del Esquema Físico DDL y Semilla de Datos

El diseño físico de la base de datos se plasmó en el script [`overtext/src/main/resources/schema-supabase.sql`](file:///Users/jonatl9/Desktop/Overtext-Web/overtext/src/main/resources/schema-supabase.sql), estructurado en 4 tablas relacionales de tercera forma normal (3FN) con índices y restricciones de integridad:

### A. Estructura de Tablas del Sistema

| Tabla | Propósito en el Negocio | Registros Semilla | Restricciones de Integridad |
|---|---|:---:|---|
| **`categoria`** | Clasificación del catálogo streetwear | 1 línea activa ("Shorts Urbanos") | `id` PK autoincremental, `slug` único |
| **`producto`** | Catálogo central de prendas y stock | 7 productos oficiales con SKU y colores | `codigo` único, `precio > 0`, `stock >= 0`, FK `categoria_id` (`RESTRICT`) |
| **`rol`** | Perfiles de autorización y acceso | 2 roles (`ADMIN`, `CLIENTE`) | `nombre` único (`VARCHAR(40)`) |
| **`usuario`** | Cuentas registradas y administradores | 2 usuarios iniciales sembrados | `email` único, hash BCrypt, FK `rol_id` (`RESTRICT`) |

### B. Extracto DDL Canónico Ejecutado en Supabase

```sql
-- Creación de la tabla categoria
CREATE TABLE IF NOT EXISTS categoria (
    id          BIGSERIAL PRIMARY KEY,
    nombre      VARCHAR(60) NOT NULL,
    slug        VARCHAR(60) NOT NULL UNIQUE,
    descripcion VARCHAR(255),
    activo      BOOLEAN NOT NULL DEFAULT TRUE
);

-- Creación de la tabla producto
CREATE TABLE IF NOT EXISTS producto (
    id               BIGSERIAL PRIMARY KEY,
    codigo           VARCHAR(40) NOT NULL UNIQUE,
    nombre           VARCHAR(100) NOT NULL,
    slogan           VARCHAR(150),
    descripcion      TEXT,
    precio           DECIMAL(10,2) NOT NULL CHECK (precio > 0),
    precio_pack      DECIMAL(10,2),
    stock            INT NOT NULL DEFAULT 0 CHECK (stock >= 0),
    imagen_principal VARCHAR(255),
    color_nombre     VARCHAR(40) NOT NULL,
    color_hex        VARCHAR(10) NOT NULL,
    correo_proveedor VARCHAR(100) NOT NULL,
    activo           BOOLEAN NOT NULL DEFAULT TRUE,
    categoria_id     BIGINT NOT NULL REFERENCES categoria(id) ON DELETE RESTRICT ON UPDATE CASCADE
);

-- Índices de alto rendimiento para consultas frecuentes
CREATE INDEX IF NOT EXISTS ix_producto_categoria ON producto(categoria_id);
CREATE INDEX IF NOT EXISTS ix_producto_activo ON producto(activo);
CREATE INDEX IF NOT EXISTS ix_usuario_rol ON usuario(rol_id);
CREATE INDEX IF NOT EXISTS ix_usuario_email ON usuario(email);
```

## 4. Configuración del Pool de Conexiones HikariCP y JPA

En aplicaciones de producción sobre microservicios o APIs REST, la creación y destrucción constante de conexiones TCP/IP a una base de datos remota en la nube introduce una latencia inaceptable. **HikariCP** es el gestor de pool de conexiones JDBC más veloz y ligero del ecosistema Java, seleccionado por defecto en Spring Boot.

En el archivo [`overtext/src/main/resources/application.properties`](file:///Users/jonatl9/Desktop/Overtext-Web/overtext/src/main/resources/application.properties), se parametrizó la conexión y el comportamiento del pool mediante variables de entorno seguras:

```properties
# ==============================================================================
# Conexión a Base de Datos Supabase (PostgreSQL) con Pool HikariCP
# Credenciales inyectadas mediante variables de entorno (Ambiente seguro)
# ==============================================================================
spring.datasource.url=${SUPABASE_DB_URL:jdbc:postgresql://aws-1-us-west-2.pooler.supabase.com:5432/postgres?sslmode=require}
spring.datasource.username=${SUPABASE_DB_USER:postgres.cdodvtruaevryrbreacm}
spring.datasource.password=${SUPABASE_DB_PASSWORD:}
spring.datasource.driver-class-name=org.postgresql.Driver

# Configuración del Pool HikariCP
spring.datasource.hikari.pool-name=OverTextHikariPool
spring.datasource.hikari.maximum-pool-size=5
spring.datasource.hikari.minimum-idle=2
spring.datasource.hikari.idle-timeout=30000
spring.datasource.hikari.connection-timeout=20000
spring.datasource.hikari.max-lifetime=1800000

# Configuración JPA / Hibernate
spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
spring.jpa.open-in-view=false
```

### Justificación de Parámetros de HikariCP:

| Parámetro HikariCP | Valor Configurado | Justificación Técnica |
|---|:---:|---|
| `pool-name` | `OverTextHikariPool` | Identificador visual explícito en los registros de log del servidor. |
| `maximum-pool-size` | `5` | Ajustado para respetar las cuotas del Session Pooler de Supabase en capa Free y evitar agotamiento de sockets en AWS. |
| `minimum-idle` | `2` | Mantiene dos conexiones vivas precalentadas para responder de inmediato sin costo de handshake TLS. |
| `idle-timeout` | `30000 ms` (30s) | Tiempo máximo de inactividad antes de liberar conexiones sobrantes del pool. |
| `connection-timeout` | `20000 ms` (20s) | Tiempo máximo de espera del hilo HTTP para obtener una conexión libre antes de disparar una excepción. |
| `max-lifetime` | `1800000 ms` (30 min) | Ciclo de vida máximo de una conexión física para prevenir caídas por timeouts silenciosos de firewalls intermedios en AWS. |
| `open-in-view` | `false` | Desactiva el antipatrón Open Session In View (OSIV), garantizando que las conexiones se liberen inmediatamente al terminar la transacción del Service. |
