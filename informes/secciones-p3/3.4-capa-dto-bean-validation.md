## 1. Propósito del Patrón DTO (Data Transfer Object)

La **Capa DTO** se sitúa entre los controladores REST y el modelo de dominio persistente. Su función es definir un contrato de datos explícito para la frontera de la API, de modo que las entidades JPA nunca se expongan directamente al cliente HTTP.

En la arquitectura multicapas de OverText esta separación resuelve cuatro problemas concretos:

- **Seguridad del dato sensible:** `UsuarioResponseDTO` **no declara** el campo `password`. El hash de la contraseña no puede filtrarse por serialización accidental, porque la clase que viaja al cliente simplemente no tiene ese atributo.
- **Control de la escritura:** `ProductoRequestDTO` omite `id` y `activo`. El cliente no puede imponer la clave primaria ni reactivar un producto dado de baja; esos valores los gobierna el backend.
- **Ruptura de ciclos de serialización:** las entidades `Categoria` y `Rol` mantienen colecciones bidireccionales (`@OneToMany`). Los DTO planos las omiten, evitando recursión infinita en el JSON y consultas innecesarias a Supabase.
- **Punto único de validación:** las reglas de formato se declaran de manera declarativa con anotaciones Jakarta Bean Validation (JSR-380), y Hibernate Validator las ejecuta automáticamente al entrar la petición, antes de que el servicio consuma el dato.

## 2. Catálogo de DTOs Implementados

Paquete `pe.edu.utp.overtext.dto`. Las clases usan Lombok (`@Data`, `@NoArgsConstructor`, `@AllArgsConstructor`), manteniendo el mismo estándar sin código repetitivo que la capa Entity.

| Clase | Dirección | Responsabilidad | Validaciones |
|---|:---:|---|:---:|
| `ProductoRequestDTO` | Entrada | Creación y actualización de productos (`POST`, `PUT`) | ✅ 5 anotaciones de la rúbrica |
| `ProductoResponseDTO` | Salida | Serialización de productos hacia Postman / cliente | — |
| `CategoriaDTO` | Salida | Información de categorías sin arrastrar el catálogo | — |
| `RolDTO` | Salida | Catálogo de roles asignables (`GET /api/roles`) | — |
| `UsuarioRequestDTO` | Entrada | Registro de usuarios (`POST /api/usuarios`) | ✅ Bean Validation |
| `UsuarioResponseDTO` | Salida | Respuesta segura de usuario, sin hash de contraseña | — |

Los DTO son **portadores de datos puros**: no contienen lógica de mapeo. La conversión `Entity ↔ DTO` reside en la capa de servicio (`ProductoServiceImpl`, `UsuarioServiceImpl`), respetando la separación de responsabilidades de la arquitectura multicapas.

## 3. Tabla de Restricciones de `ProductoRequestDTO`

Esta clase concentra las **cinco anotaciones exigidas por la rúbrica de la P3**: `@Size`, `@Email`, `@NotNull`, `@Positive` y `@NotBlank`.

| Atributo | Tipo | Anotaciones Bean Validation | Mensaje al cliente |
|---|:---:|---|---|
| `codigo` | `String` | `@NotBlank` | *El código es obligatorio* |
| `nombre` | `String` | `@NotBlank`, `@Size(min = 3, max = 100)` | *El nombre es obligatorio* / *Debe tener entre 3 y 100 caracteres* |
| `slogan` | `String` | *(opcional)* | — |
| `descripcion` | `String` | *(opcional)* | — |
| `precio` | `Double` | `@NotNull`, `@Positive` | *El precio es obligatorio* / *El precio debe ser mayor a 0* |
| `precioPack` | `Double` | `@PositiveOrZero` | *El precio de pack no puede ser negativo* |
| `stock` | `Integer` | `@NotNull`, `@PositiveOrZero` | *El stock es obligatorio* / *El stock no puede ser negativo* |
| `imagenPrincipal` | `String` | *(opcional)* | — |
| `colorNombre` | `String` | `@NotBlank` | *El nombre del color es obligatorio* |
| `colorHex` | `String` | `@NotBlank` | *El código hexadecimal es obligatorio* |
| `correoProveedor` | `String` | `@NotBlank`, `@Email` | *El correo es obligatorio* / *Debe ser un correo electrónico válido* |
| `categoriaId` | `Long` | `@NotNull`, `@Positive` | *La categoría es obligatoria* / *El ID de categoría debe ser válido* |

> **Nota sobre tipos:** se respeta el contrato canónico del proyecto (`Double` para precios, `Integer` para stock, `Long` para identificadores). No se emplea `BigDecimal` ni tipos primitivos, garantizando interoperabilidad con las capas Entity, Repository y Service sin conversiones implícitas.

### Diferencia entre las anotaciones de obligatoriedad

| Anotación | Rechaza | Aplicación en OverText |
|---|---|---|
| `@NotNull` | Solo el valor `null` | Numéricos (`precio`, `stock`, `categoriaId`), donde un `0` es semánticamente distinto de un valor ausente |
| `@NotBlank` | `null`, cadena vacía y cadena de solo espacios | Textos obligatorios (`codigo`, `nombre`, `colorHex`) |
| `@Positive` | Cero y valores negativos | `precio` y `categoriaId`, donde el cero carece de sentido de negocio |
| `@PositiveOrZero` | Solo valores negativos | `stock` y `precioPack`, donde el cero es un estado legítimo (agotado / sin pack) |

## 4. Tabla de Restricciones de `UsuarioRequestDTO`

| Atributo | Tipo | Anotaciones Bean Validation | Mensaje al cliente |
|---|:---:|---|---|
| `email` | `String` | `@NotBlank`, `@Email` | *El email es obligatorio* / *Debe ser un correo electrónico válido* |
| `password` | `String` | `@NotBlank`, `@Size(min = 6)` | *La contraseña es obligatoria* / *La contraseña debe tener al menos 6 caracteres* |
| `nombre` | `String` | `@NotBlank`, `@Size(min = 3, max = 100)` | *El nombre es obligatorio* / *Debe tener entre 3 y 100 caracteres* |
| `rolId` | `Long` | `@NotNull`, `@Positive` | *El rol es obligatorio* / *El ID de rol debe ser positivo* |

La contraseña se recibe en claro **únicamente** para que la capa de servicio la cifre antes de persistirla. El DTO de respuesta correspondiente (`UsuarioResponseDTO`) expone solo `id`, `email`, `nombre`, `activo` y `rolNombre`.

## 5. Trazabilidad frente al Criterio de la Rúbrica

El criterio de `P3.md` exige *al menos un DTO con validaciones `@SIZE`, `@EMAIL`, `@NOTNULL`, `@POSITIVE` y `@NOTBLANK`*. Las cinco se verifican en una sola clase:

| Anotación exigida | Clase | Atributos donde se declara |
|:---:|---|---|
| `@NotBlank` | `ProductoRequestDTO` | `codigo`, `nombre`, `colorNombre`, `colorHex`, `correoProveedor` |
| `@Size` | `ProductoRequestDTO` | `nombre` (`min = 3`, `max = 100`) |
| `@NotNull` | `ProductoRequestDTO` | `precio`, `stock`, `categoriaId` |
| `@Positive` | `ProductoRequestDTO` | `precio`, `categoriaId` |
| `@Email` | `ProductoRequestDTO` | `correoProveedor` |

Estas anotaciones se activan en el controlador mediante `@Valid @RequestBody ProductoRequestDTO dto` (Capítulo 3.5), y el `GlobalExceptionHandler` traduce las violaciones a una respuesta **HTTP 400 Bad Request** con la lista de mensajes en formato JSON.

## 6. Comportamiento Esperado en la Frontera de la API

**Petición válida**, que produce `HTTP 201 Created`:

```json
{
  "codigo": "OT-SHORT-008",
  "nombre": "Short Urbano Guinda",
  "precio": 89.90,
  "precioPack": 159.90,
  "stock": 24,
  "colorNombre": "Guinda",
  "colorHex": "#6E1423",
  "correoProveedor": "proveedor@overtext.pe",
  "categoriaId": 2
}
```

**Petición inválida**, que produce `HTTP 400 Bad Request`. Un cuerpo con `nombre` de 2 caracteres, `precio` negativo, `stock` ausente y correo mal formado dispara simultáneamente `@Size`, `@Positive`, `@NotNull` y `@Email`, devolviendo los mensajes en español definidos en las tablas anteriores. Esta es la evidencia registrada en la **Captura 12** del informe.

La respuesta de consulta (`ProductoResponseDTO`) aplana la relación con la categoría en un JSON de un solo nivel:

```json
{
  "id": 8,
  "codigo": "OT-SHORT-008",
  "nombre": "Short Urbano Guinda",
  "precio": 89.90,
  "stock": 24,
  "correoProveedor": "proveedor@overtext.pe",
  "activo": true,
  "categoriaId": 2,
  "categoriaNombre": "Shorts Urbanos"
}
```

## 7. Verificación Automatizada de las Validaciones

Para demostrar el funcionamiento de las restricciones de forma independiente de la capa REST, se implementó la prueba unitaria `ProductoRequestDTOValidationTest` (`src/test/java/pe/edu/utp/overtext/dto/`). Esta instancia el `Validator` de Jakarta directamente, sin levantar el contexto de Spring ni consultar Supabase:

| Caso de prueba | Resultado esperado |
|---|---|
| DTO completo y correcto | Cero violaciones |
| `nombre = "AB"`, `precio = -10.0`, `stock = null`, `codigo = ""` y correo mal formado | Violaciones en los 5 campos (`@Size`, `@Positive`, `@NotNull`, `@NotBlank`, `@Email`) |
| `categoriaId = null` y `categoriaId = -5` | Violación de `@NotNull` y de `@Positive` respectivamente |
| `UsuarioRequestDTO` con contraseña de 3 caracteres y email sin arroba | Violaciones de `@Size(min = 6)` y `@Email` |

**Resultado de la ejecución:** `Tests run: 8, Failures: 0, Errors: 0` sobre la suite completa del proyecto (4 pruebas de validación de DTO más 4 pruebas de conexión y consulta contra Supabase), con `BUILD SUCCESS`.
